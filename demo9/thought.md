# Question

- **Q：什么是 HITL（Human-in-the-Loop）？为什么可用系统追求的是"更可控"而不是"更自动"？**
  A：在 Agent 流程的关键决策点把执行权交还给人。自动化的收益是省人力，代价是错误也被放大自动化——一次错误落盘 × 无限循环 = 灾难。HITL 把自动化失败的代价封顶：最坏情况是"人拒绝了一次修改"，而不是"文件被改坏了"。

- **Q：plan → approval → apply 两阶段拆分的本质是什么？**
  A：把"意图"和"副作用"分离。模型生成计划是纯计算，零风险，可以随便重试；写文件是有副作用的不可逆动作。审批节点正好卡在两者之间——决策点被前移到不可逆动作发生之前，而不是事后补救。

- **Q：审批节点用阻塞的 `input()` 实现，意味着什么？真实系统怎么做？**
  A：demo 里整个 workflow 进程停下来等人，上下文全在内存里——简单但脆弱（进程挂了状态就丢了）。真实系统是"暂停/恢复"模型：把状态持久化（checkpoint），人工审批是异步事件，批完再恢复执行。LangGraph 的 interrupt + checkpoint 就是这个模式。

- **Q：`SafeApplyNode` 为什么落盘前还要再检查一次 `approved`？审批节点不是已经拦过了吗？**
  A：纵深防御。路由是配置出来的，可能配错、可能被绕过（比如未来有人新接一条边直达 apply）；提示词约束是软的。但"没批准就不许写文件"这道检查写死在 apply 节点内部，无论流程怎么改都不会失效——关键约束要放在离副作用最近的地方，而不是只依赖上游流程。

- **Q：修改意见重试怎么防止死循环？**
  A：两道保险。第一道是显式的 `max_revisions`（本 demo 为 2），修订预算用完再选重试就视为拒绝；第二道是 `max_steps` 兜底（即使上限逻辑写错了，路由成环也会被熔断）。另外修订后的计划要**重新过 risk_check**——人要的计划也可能和文件现实不符，人工意见不能免检。

- **Q：`approval_required=False` 和 summary 任务跳过审批，说明了什么设计？**
  A：分级审批。只读操作（list/search/read、总结类任务）无副作用，免审；写操作必审。审批本身有人力成本，不加区分地什么都审，人会在疲劳中机械点"同意"——审批就形同虚设了。所以豁免低风险动作反而是在保护审批质量。

- **Q：HITL、权限系统、沙箱三者是什么关系？**
  A：三个正交的安全层。沙箱（demo7 的 workspace 边界）限制"能碰哪里"——执行边界；审批（demo9）决定"这次能不能做"——授权决策；权限系统是两者的静态化版本（白名单规则代替逐次询问）。demo9 叠在 demo7 之上：文件就算改，也只能改工作区里的，且改之前要过人。

- **Q：`human_feedback` 有什么双重价值？**
  A：既是下一轮修订的输入（喂给 RevisePlanNode 重新生成计划），也是审计记录（logs 里留了拒绝原因）。拒绝不是流程的终点，而是最宝贵的新信息——人为什么说不，往往就是计划缺的那一块。

- **Q：审批界面为什么要展示 diff 和出现次数核对，而不是贴出旧文和新文全文？**
  A：审批质量取决于展示质量。diff 让人只看变化（认知负荷从 O(全文) 降到 O(变化)）；出现次数"实际 N / 预期 M"给了人一个不用读代码就能核对的客观数据，不一致本身就是危险信号。人在审批时最容易被大段文本淹没而放过关键改动。

- **Q：真实产品里的 HITL 长什么样？**
  A：Claude Code 的权限模式（默认逐次确认、allowed-tools 白名单放行、审计留痕）；GitHub Actions 的 environment protection rules（生产部署要指定审批人点批准）；支付/风控的二次确认。共同点：默认拒绝、按规则豁免、全量审计——和本 demo 的 approval_required / 分级跳过 / logs 是同构的。

# Practice 完成记录

## 前置：修复一个跨 demo 回归

- demo8 练习把 `PlanNode` 的 action 从 `apply` 改成 `risk_check` 后，demo9 原来的 `plan.connect("apply", approval)` 永远匹配不上，流程会在 plan 后静默停止
- 修法是把 demo8 的 `RiskCheckNode` 也接进 demo9：plan → risk_check → approval → apply，**机器门在人工门之前**——明显不合格的计划先被程序拦下，不浪费人的注意力
- 教训：跨 demo 复用节点时，action 字符串是隐性契约，改一端的返回值要全局搜另一端的 connect

## 练习一：审批节点增加"修改意见后重试"分支

- `ApprovalNode` 从两分支变三分支：yes（批准）/ r（按修改意见重试）/ 其他（拒绝）
- 新增 `RevisePlanNode`：把"原计划 + 人工修改意见 + 文件快照"交给模型输出修订计划；修订计划回到 risk_check 重新过机器门，再回 approval 重新审——新计划不因"是人要的"免检
- 防死循环双保险：`max_revisions=2`（用尽后再选 r 视为拒绝）+ `MAX_WORKFLOW_STEPS=14`（按最长路径 4+6+4 推导）
- 上下文新增 `revision_count` / `max_revisions`，报告节点带上修订轮数

## 练习二：审批展示改得适合人工审阅

- 旧文/新文整段对照改为 **unified diff**（difflib 渲染，超 60 行截断提示）——人只看变化
- 新增**出现次数核对**：读当前文件实际数一遍 old_text 出现次数，和计划声明的 expected_occurrences 并排展示，不一致直接标注"需要留意"
- 修订轮次提示（"第 N 轮修订后"）、操作选项说明（yes / r / 其他）显式打印

# idea

- 判断三个问题：**可逆吗？影响面多大？错了谁负责？**——三个都"轻"就可以自动，任何一个"重"就应该人审
- 必须人审的动作（不可逆 / 对外 / 资金 / 合规）：删数据、发版部署、发邮件和消息（对外发布）、支付和退款、生产库 migration、删除大量文件
- 可以自动的动作（可逆 + 局部 + 有兜底）：本仓库的文件修改就属于此类——有 verify 读回验证、有沙箱限制范围、有 git 可回滚；只读操作（搜索、总结）永远免审
- 中间地带用**风险分级 + 采样**：低风险全自动，高风险逐条人审，中风险批量展示 diff 快速审；审批也要控制人力成本，否则人会疲劳性全点同意
- 审批的粒度 = 信任的粒度：Claude Code 的 allowed-tools 白名单本质上是"这类动作我审过了，同类以后免审"——把逐次审批泛化成规则
- 关键洞察：HITL 不是降低自动化程度，而是**给自动化失败的代价封顶**。demo9 的流程和 demo8 一样自动，唯一区别是"写文件"这一步的失败模式从"可能改坏"变成"最多被拒绝"
